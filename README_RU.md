# glovo-export

[English](README.md) · **Русский**

Локальная CLI-утилита: выгружает историю твоих заказов Glovo и Amazon в нормализованный JSON.

## Зачем

В интерфейсе Glovo историю заказов нельзя ни отфильтровать, ни выгрузить. Данные при этом лежат за нормальным JSON API — их надо просто собрать, привести к числам и посчитать. JSON на выходе рассчитан на то, чтобы поверх него потом построить графики.

С Amazon та же история, только API хуже: для покупателей его нет вообще, есть только страницы истории заказов. Поэтому [часть про Amazon](#amazon) читает эти страницы — в твоём же браузере, под твоей же сессией — и пишет JSON той же формы.

## Как это работает

Ключевое решение: **все запросы к API выполняются внутри страницы**, через `page.evaluate` на `https://glovoapp.com`. Node оркеструет процесс, но токен не видит никогда.

```
Node (tsx)                     Chromium (профиль Playwright)
  |                              |
  |-- page.evaluate(fetch) ----->|  читает cookie glovo_auth_info
  |                              |  fetch -> api.glovoapp.com
  |<---------- JSON -------------|
  |
  нормализация -> валидация -> out/*.json
```

Это одним решением закрывает сразу четыре проблемы:

- **CORS.** API пускает только origin `https://glovoapp.com` (точное совпадение, даже `www` не подходит). Запрос со страницы этого же домена проходит по определению.
- **Токен живёт 20 минут.** Cookie читается заново перед каждым запросом, поэтому протухнуть посреди выгрузки нечему.
- **Refresh-токен не трогаем.** `POST /oauth/refresh` не вызывается, ротацией занимается сама страница. При `401` мы просто перезагружаем страницу и повторяем запрос.
- **Безопасность.** Токен не попадает ни в память Node, ни на диск, ни в логи.

Авторизацию выполняет человек — руками, в открытом окне браузера (на странице логина есть reCAPTCHA, и автоматизировать это не нужно). Сессия сохраняется в постоянном профиле Playwright `~/.glovo-export/profile`, поэтому логиниться заново при каждой выгрузке не требуется.

### Сбор заказов

1. `GET /v3/customer/orders-list?offset=<cursor>&limit=50` — курсорная пагинация. Важно: `offset` это **id следующего заказа**, а не номер строки.
2. Список — «презентационный»: в нём нет ни дат, ни цен по позициям. Поэтому по каждому заказу нужен отдельный запрос `GET /v3/customer/orders/{id}`.
3. Заказы отсортированы от новых к старым, id монотонны — значит детали тянем сверху вниз и останавливаемся после **3 подряд** заказов вне запрошенного диапазона (три, а не один, чтобы единичная аномалия не обрезала выгрузку).

Темп: 750 мс между страницами списка, 1000 мс между заказами. Ретраев максимум 5. На `429` — пауза `min(15000 * 2^попытка, 120000)` мс, на `5xx` — `min(1000 * 2^попытка, 30000)` мс.

### Нормализация — самая ответственная часть

Каждое правило ниже получено измерением на живых данных, а не из документации:

| Поле | Правило |
|---|---|
| Дата | Берём `currentStatus.creationTime` (epoch ms). Поле `creationTime` в корне **всегда `null`** — читать его нельзя |
| Деньги | `"12,00 €"`, `"8,34 EUR"`, `"No cost"` → число. Запятая как десятичный разделитель, `"No cost"` = 0. Не распарсилось → `null` **и предупреждение**, никогда не молчаливый `0` |
| Цена позиции | `price` — это сумма по строке, **не цена за штуку**. Умножать на количество нельзя. `unitPrice` считаем отдельно |
| Неоплаченные позиции | Строки с `displayStyle === "STRIKETHROUGH"` (товара не оказалось) несут ненулевую цену, которую никто не платил. Из сумм исключаем, но в выгрузке оставляем с `charged: false` |
| Скидки | `price` уже с учётом промо. Сохраняем `originalLineTotal` (из `originalPrice`) и `discount` — отрицательное число. Если `promotionDescription` содержит сумму (`"-2,50 €"`), берём её; иначе считаем как `price - originalPrice`. Промо вида `"-20%"` или `"2x1"` суммой не являются — их не парсим |
| Отменённые | Отмену читаем из `currentStatus.type` (`CanceledStatus`), а не только из `recentlyCancelled` — второе поле значит «отменён недавно» и на старых заказах пустое. У отменённых `TOTAL` отсутствует, поэтому они помечаются `excludedFromSpend: "cancelled"` и в сумму не идут |
| Возвраты | `refunded` помечаем, но сумму **оставляем в тратах**: API не сообщает, сколько именно вернули, а `TOTAL` — это то, что реально списали. В отчёте возвраты показываются отдельной строкой, а не вычитаются молча |

Определять «не оплачено» нужно строго по `displayStyle`, а не по тексту `notice` — текст локализованный.

**Персональные данные вырезаются всегда**: `points[]` (точка `DELIVERY` — это домашний адрес, самое чувствительное поле во всём ответе), блок `PAYMENT` (последние 4 цифры карты), HTML-теги из `shortSummary`. Для графиков ничего из этого не нужно.

### Валидация

По каждому заказу проверяем: `сумма оплаченных позиций ≈ строка PRODUCTS` (допуск 1 цент). Результат кладём в `validation.productsMatch` и `validation.delta`.

Важно понимать, что это значит на практике. Расхождения — **нормальное свойство данных Glovo**, а не баг парсера: в продуктовых заказах позиции меняются уже после сборки (`notice` прямо называет причины: `"Price change"`, `"Product added"`, `"Not available"`). На реальной выгрузке разошлись 36 заказов из 168, отклонения от −1,35 € до +8,29 € в обе стороны. Скрытого поля с фактически списанной ценой позиции в ответе нет — проверено по полному списку полей.

Поэтому: **`PRODUCTS` и `TOTAL` — источник истины**, это то, что реально списали. Итоговая сумма трат считается по `totals.total` и верна. А `productsMatch` читается как флаг качества данных для графиков по позициям.

## Что используем

- **TypeScript** + **tsx** (без сборки)
- **Playwright** — единственная runtime-зависимость, нужна ради `launchPersistentContext`
- Разбор аргументов — встроенный `node:util` `parseArgs`, тесты — встроенный `node:test`

Больше ничего. Общее ядро лежит в `src/core/` (`normalize.ts` + `types.ts`): ни одного runtime-импорта и ни одного node-builtin, поэтому тот же код запускается и в Node, и в браузере. Ядро чистое: фикстуры на вход, объекты на выход, без сети — тестируется без браузера.

Читалка Amazon лежит в `src/amazon/`: `extract.ts` — функции, которые выполняются внутри страницы, `locale.ts` — таблицы подписей для испанского и английского, `normalize.ts` — приведение к общей форме заказа. Экстракторы тестируются на синтетических HTML-фикстурах в настоящем Chromium, всё остальное — без него.

## Использование

```bash
npm run login
```

Откроется окно браузера. Логинишься сам. После входа команда печатает claims токена (`userId`, `grantType`, `role`, срок действия) — чтобы убедиться, что это нужный аккаунт.

```bash
npm run export -- --from 2025-01-01 --to 2026-12-31
```

Флаги: `--out <путь>` (по умолчанию `out/glovo-orders-<год>-<год>.json`), `--expect-user <id>` — не запускать выгрузку, если в сессии другой аккаунт.

Проверка кода:

```bash
npm test
npm run typecheck
```

## Amazon

Для покупателей у Amazon нет API истории заказов, поэтому эта часть — **читалка страниц**. Она открывает историю заказов в своём отдельном постоянном Chromium, страницу за страницей, и снимает поля с отрендеренного HTML. Код чтения выполняется *внутри страницы* (`page.evaluate`) и возвращает только именованные поля — id, даты, суммы, названия, ASIN, количества, продавцов, текст статуса. Сама страница в Node не попадает.

```bash
npm run amazon:login                                          # логинишься сам в открывшемся окне
npm run amazon:probe                                          # грузит одну страницу списка, печатает только счётчики
npm run amazon:export -- --from 2025-01-01 --to 2025-12-31
```

Флаги: `--marketplace amazon.es` (по умолчанию; любой `amazon.<tld>`), `--out <путь>` (по умолчанию `out/amazon-orders-<год>-<год>.json`), `--headless` (только для export; по умолчанию выключен, см. ниже). Перед первой выгрузкой запусти `amazon:probe`: он покажет, жива ли сессия, на каком языке приходят страницы и у каждой ли карточки на странице нашлись id, дата и сумма.

### Как читает

- `/your-orders/orders?timeFilter=year-YYYY&page=N` по каждому году диапазона, затем `/your-orders/order-details?orderID=…` по каждому заказу с датой внутри него. Одна вкладка, последовательно: 1 с между страницами списка, 1,5 с между заказами. Триста заказов — примерно десять минут.
- **Окно браузера видно намеренно — в отличие от выгрузки Glovo.** Glovo отдаёт JSON через API, и его проверка на бота бывает только при входе, поэтому `npm run export` работает без окна. Amazon отдаёт страницы, и капча, проверка WAF или повторный вход могут появиться на любой из них, посреди выгрузки. После каждой загрузки утилита ищет известные признаки проверки; если нашла — печатает сообщение и до пяти минут ждёт, пока *ты* пройдёшь её в окне, потом продолжает. Сама она ничего не решает, не проксирует и не подделывает.
- **`--headless` — когда сессии уже доверяешь.** Тот же обход, без окна. Проверка всё равно распознаётся, но решить её негде: утилита ждёт пять минут, падает с ошибкой, и ты перезапускаешь с окном. Пробу и первую полную выгрузку делай с окном; на `--headless` переходи для следующих запусков, если ни один из них не упёрся в проверку. Скрытый Chromium к тому же чуть чаще ловит проверку, чем видимый.
- **Страницы локализованы.** `?language=en_US` на amazon.es игнорируется (побеждает cookie языка самого сайта), поэтому ничего не берётся по позиции — каждая подпись проходит через таблицы для испанского и английского в `src/amazon/locale.ts`: заголовки карточек, строки итогов (`Subtotal de producto(s)` / `Items`, `Envío` / `Postage`, `Importe total` / `Grand Total`, …), `Vendido por:` / `Sold by:`, слова отмены и возврата, названия месяцев. Другой язык даёт предупреждение `unsupported_locale`, сырые строки сохраняются; добавить язык — значит добавить таблицу.
- **Та же форма JSON, что у Glovo.** `store` — продавец (`Amazon` для собственных продаж, иначе id и имя продавца); у позиций добавлен `asin`; `vertical` — `null`; `date` — просто `YYYY-MM-DD`, потому что время заказа Amazon не показывает. `totals.products` / `delivery` / `total` берутся из итогов заказа, `validation.productsMatch` сверяет `unitPrice × quantity` с подытогом по позициям с тем же допуском в 1 цент.

### Что не сохраняется никогда

На странице заказа есть твоё имя, адрес доставки, способ оплаты, цифры карты и ссылки на счета. **Ничего из этого не попадает ни в выгрузку, ни в Node.** Экстрактор списка целиком пропускает блок «Enviar a» / «Ship to»; экстрактор деталей читает строки итогов и сетку позиций и никогда не заходит в блок с адресом, покупателем и виджетом оплаты.

Это не обещание, а тест: `test/amazon-extract.test.ts` загружает синтетическую страницу заказа, в которой *специально* лежат выдуманные имя, улица, `•••• 4242` и ссылка на счёт, прогоняет по ней настоящий экстрактор в Chromium и проверяет, что ни одна из этих строк не уцелела. Свою первую выгрузку можно проверить, не открывая файл:

```bash
grep -ciE 'enviar a|ship to|calle|street|visa|mastercard|••••|método de pago|payment' out/amazon-orders-*.json
```

Должно быть `0`.

`~/.glovo-export/amazon-profile` — живая сессия Amazon, правило то же, что и для профиля Glovo: не копировать, не синхронизировать, никому не отдавать. Удалил папку — сессия закончилась.

### Ограничения

- Только то, что показывают страницы заказов. Заказы без страницы деталей (цифровые покупки, часть совсем старых) выгружаются по одной карточке списка — с предупреждением `detail_unavailable` и позициями без цен.
- Архивные заказы не читаются. Суммы возвратов неизвестны — `refunded` только флаг, в тратах остаётся списанное.
- `status` — собственный текст страницы (`Entregado el 14 de marzo`, `Delivered 14 March`), сохраняется как есть. Заказ считается `cancelled`, только если это сказано про каждую посылку; частично отменённый остаётся в тратах с предупреждением `partial_cancellation`.
- Amazon меняет разметку без предупреждения. Если у карточки не нашёлся id или встретилась неизвестная подпись, выгрузка предупреждает (`missing_order_id`, `unmatched_header_label`), а не угадывает.

## Формат выгрузки

```json
{
  "meta": {
    "source": "glovo",
    "exportedAt", "accountUserId", "grantType", "accountRole",
    "range", "ordersSeen", "ordersExported", "requestCount", "warnings": []
  },
  "orders": [{
    "id", "date", "store": { "id", "name", "slug" },
    "status", "cancelled", "refunded", "excludedFromSpend", "vertical", "currency", "summary",
    "items": [{
      "name", "quantity", "lineTotal", "originalLineTotal", "discount",
      "unitPrice", "charged", "notice", "customizations", "promotion", "freeProduct"
    }],
    "totals": { "products", "delivery", "total", "lines": [] },
    "validation": { "productsMatch", "delta" }
  }]
}
```

У выгрузки Amazon `"source": "amazon"`, а вместо claims аккаунта и `requestCount` — `marketplace` и `pagesLoaded`; у позиций есть дополнительное поле `asin`. Файлы без `source` — выгрузки Glovo, сделанные до появления этого поля.

## Ограничения

- Выгружается история **того аккаунта, под которым вошли**. Если заказы разнесены по нескольким аккаунтам (например, вход по паролю и вход через Google), придётся выгружать каждый отдельно и склеивать по `id`.
- `--expect-user` сверяет `userId` из токена. В текущем формате токена claims верхнего уровня — это `role` / `payload` / `jti`, а сам `userId` лежит внутри `payload`, поэтому он распаковывается отдельно. Если в токене `userId` не найдётся вообще, флаг честно откажется запускать выгрузку, вместо того чтобы делать вид, что проверил.
- `out/` в `.gitignore` — это персональные данные, в репозиторий они не попадают.

- Возврат помечается флагом `refunded`, но точную сумму возврата API не сообщает — поэтому она не выдумывается: в тратах остаётся то, что реально списали (`TOTAL`), а возвраты показываются отдельной строкой.

## Графики без интернета

В репозитории лежит `viewer.html` — один файл, без зависимостей и без сборки.

```bash
open viewer.html      # macOS; на Linux — xdg-open, на Windows — просто двойной клик
```

Перетащи в окно выгруженный JSON. Посчитаются: траты по месяцам, рестораны против магазинов, топ заведений, размер чека, время заказа, что берёшь чаще всего, и примерные калории.

Выгрузка Amazon получает ту же страницу с другими разрезами: Amazon против сторонних продавцов, топ продавцов по тратам, что берёшь чаще всего у каждого продавца. Время заказа и карточки калорий скрыты — у дат Amazon нет времени, а правила калорий — это названия продуктов.

### Калории — это оценка, а не измерение

Последние три карточки оценивают ккал, БЖУ, деление «лучше/хуже» и разбивку по категориям. **Базы питания за этим нет** и никуда ничего не запрашивается: всё считается по ключевым словам в названии товара (`pollo` — 120 ккал/100 г, `pizza` — 280 ккал за штуку, `cerveza` — 45 ккал/100 мл), граммы и миллилитры вытаскиваются из названия (`500 g`, `1,5 L`, `33 cl`), а если их там нет — берётся дефолт правила.

Значит: товары, которые ни под одно правило не попали, считаются как **ноль** — поэтому карточка показывает долю распознанных позиций, а суммы — это нижняя граница, а не итог. Непищевые позиции (бытовая химия, корм) распознаются и исключаются. Порции в ресторанах гуляют сильно. Читать стоит как порядок величины, не больше.

Правила — испанские и каталанские ключевые слова, под рынки, где работает Glovo. Они лежат обычным массивом в начале блока `<script>` в `viewer.html` — правь под свою корзину. Интерфейс самой страницы — английский; суммы форматируются по локали браузера.

Страница не делает ни одного сетевого запроса — файл читается через `FileReader`, всё считается в браузере. Проверить можно самому: открой вкладку Network в devtools и перетащи файл.

## Приватность

- **Данные не покидают компьютер.** Ни выгрузка, ни `viewer.html` никуда ничего не отправляют. Никакого сервера у этой утилиты нет.
- **Токен не попадает в Node.** Все запросы к API идут внутри страницы через `page.evaluate`; cookie читает браузер, а не наш процесс. На диск и в логи токен не пишется.
- **Refresh-токен не трогаем вообще.**
- **Адрес и карта вырезаются на этапе нормализации** — `points[]` и блок `PAYMENT` в выгрузку не попадают.
- **Amazon: имя, адрес и способ оплаты не покидают страницу.** Экстракторы возвращают только именованные поля и пропускают блоки, где всё это лежит; тест с выдуманными адресом и картой проверяет это при каждом запуске. См. [Что не сохраняется никогда](#что-не-сохраняется-никогда).
- **`~/.glovo-export/profile` — это живая сессия Glovo, `~/.glovo-export/amazon-profile` — живая сессия Amazon.** Папки нельзя копировать, класть в облако или кому-то передавать: у того, кто их получит, будет доступ к аккаунту. Чтобы убить сессию, достаточно удалить папку.
- Выгрузка (`out/*.json`) — персональные данные. `.gitignore` их уже закрывает, но следи за тем, куда кладёшь файл.

Утилита работает **на твоей машине, под твоей же сессией**, и читает только твои собственные заказы — как если бы ты открыл историю в браузере и переписал её вручную. Никакой третьей стороне доступ не передаётся (п. 2.2 условий Glovo — про передачу доступа к аккаунту третьим лицам). Решение пользоваться утилитой — твоё; ответственность за это тоже.

Данные берутся из внутреннего API Glovo и со страниц заказов Amazon — и то, и другое никем не задокументировано и может измениться в любой момент. Тогда парсер сломается — это ожидаемое свойство такого инструмента.

Условия использования Amazon запрещают автоматизированный доступ к сервису без согласия. Утилита работает в твоём же браузере, под твоей же сессией, в человеческом темпе и читает только твои собственные заказы — ничего, чего ты не получил бы сам, сидя за клавиатурой. Приемлемо ли это для тебя — твоё решение, как и в случае с Glovo.
